# 实现100万NPS提升评估速度

> 文档目的：客观分析从 11万 NPS 向 100万 NPS 迈进的瓶颈与突破策略。

## 📅 2026-03-08：前期状态重建优化方案

### 当前瓶颈的初步定位与后续修正

早期通过 Dumb Eval 对照实验观察到，`move_piece` 中的状态重建是显著的开销来源之一：

```python
# game_logic.pyx L115-127 —— 每次搜索节点都执行
new_board_list = [list(row) for row in self.board]     # ① 5 个 tuple→list 转换
new_board_list[end_r][end_c] = piece                   # ② 修改（唯一有用的工作）
new_state.board = tuple(tuple(row) for row in ...)     # ③ 5 个 list→tuple 转换
```

根据独立的微基准测试（`scripts/board_speed_demo.pyx`），这段代码如果转换为极致的 C 原生数据结构操作，其吞吐量可大幅提升。

① 和 ③ 各触发 5 次 Python 对象创建+销毁。在 11 万 NPS 下，每秒发生 **110 万次** 微小内存分配/释放，这对 Python 内存管理器（pymalloc）造成了很大的压力。

*（注：早期曾误认为此环节为“唯一的性能天花板”，但后续全面的 cProfile 分析证实，其他环节如 `evaluate_board` 同样存在且贡献了更大的对象分配开销。详见后文实测数据部分。）*

### 优化方案评估与选择

在针对对象分配开销进行优化时，前期评估了以下技术路线：

* **方案 A（原位操作 / Make-Unmake）**：搜索时不创建新状态，直接在单一 C 数组上执行和撤销移动。理论上限最高，但全面重构成本极大。
* **方案 B（C 数组 + 内存块复制）**：保留原有的状态不可变语义，将底层迁移至 C 一维数组（`int[25]`），通过 `memcpy` 快速克隆。在控制风险的前提下，能有效消除棋盘状态克隆的耗时。
* **方案 C（局部重建优化）**：仅微调 `move_piece` 热路径内部的元组拼接，不改底层存储。改动极小，但收益非常有限。

**实际实施路径**：
系统已选择并落地了 **方案 B（C 数组 + 内存块复制）**。这作为一种折中手段，在不破坏架构兼容性的情况下，扫除了状态复制的底层障碍。

## 📅 2026-03-09 更新：实测数据与前期误判复盘

### 1. 前期预判的失误与现状

在本文档初版中，提出“评估函数开销为零”、“瓶颈完全由数据拷贝决定”的结论。该结论已通过实际分析证实存在误差。

之前的结论基于孤立的微基准测试。该测试仅测量了单纯的数组拷贝操作，脱离了真实的上下文，编译器的死代码消除掩盖了其他部分的耗时。

**实际运行结果**：

* 实施数组与内存拷贝后，每秒节点数从 11万 提升至 14.1万（+30%）。
* 距离预期的 50万 目标存在差距。证实了状态拷贝并非唯一的短板。

### 2. 真实性能剖析

通过向核心文件注入编译指令抓取性能分析数据。总耗时约 2.85 秒的采样区段中，纯耗时排名前十的调用情况如下：

| 排名 | 函数/模块定位                      | 纯耗时  | 占比   | 开销来源概述                                       |
| :--- | :--------------------------------- | :------ | :----- | :------------------------------------------------- |
| 1    | `_quiescence_search`               | 0.518秒 | 18.2%  | 静默搜索中的逻辑判断及函数调用开销。               |
| 2    | `_calculate_control_zone_bfs`      | 0.441秒 | 15.5%  | 计算控制区。产生双端队列及元组对象。               |
| 3    | `evaluate_board`                   | 0.338秒 | 11.8%  | 静态评估主框架。包含子函数调用及分数加权计算逻辑。 |
| 4    | `get_valid_moves`                  | 0.316秒 | 11.1%  | 走法遍历及包装。生成并返回包含嵌套元组的列表对象。 |
| 5    | `_calculate_soldier_scores`        | 0.289秒 | 10.1%  | 计算兵营与前线分。依赖嵌套循环迭代处理。           |
| 6    | `_calculate_cannon_forbidden_zone` | 0.284秒 | 10.0%  | 计算火炮禁区。底层调用集合添加操作引发内存处理。   |

| 9    | `is_set`                           | 0.028秒 | < 1.0% | 线程机制的信号状态检查。                           |

**客观解读**：
排名前十的调用占据了核心计算时间。其中排名第 2、3、5、6 均从属于单次宏观静态评估，合计时间占比约 47.4%。排名第 4 的走法生成部分单独占用约 11.1%。初步观察认为，这些环节中对内存动态对象（如集合、列表、元组、双端队列）的依赖，可能是限制运行速度的因素，有待进一步通过原型代码进行验证。

### 3. 下一步优化验证建议

为验证内置对象操作是否为主要的性能阻碍，建议在下一阶段从以下方向进行局部验证与改写：

**建议方向 1：简化评估逻辑**

* 思路：尝试减少评估函数中双端队列和集合的使用。转而测试基于整型数组的线性迭代，观察其对内存及查询速率的影响。

**建议方向 2：静态化走法集**

* 思路：探索是否能避免每次都返回独立的列表和元组结构。可通过传入固定定长数组的指针用于结果收集，观察对吞吐量的实际改善效果。

**建议方向 3：原位操作验证**

* 思路：在以上逻辑清理完成后，再行评估将目前的增量克隆模式改写为原地修改并在回溯时还原的操作方式，通过基准测试量化其收益。
