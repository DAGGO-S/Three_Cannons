# 核心引擎零分配重构与极速优化报告 (Zero-Allocation Refactor)

> **文档状态**：已完结 (闭环归档)
> **文档目的**：全局整合本项目从 11万 NPS 向近 60万 NPS 迈进的底层 C 语言化降维重构过程、性能剖析数据及突破策略。

## 一、 重构背景与基线测算

在初始形态下，AI 引擎受到 Python 垃圾回收 (GC) 与运行时对象分配的严重制约。
- **初始瓶颈**：每一次走子（`move_piece`）与走法生成（`get_valid_moves`）均涉及大量 `tuple` 和 `list` 的重复推导。
- **初始基线**：标准开局 Depth=12 的无探针裸跑速度仅约 **110,000 NPS**。
- **核心目标**：消除博弈树搜索热点路径中的动态内存分配，将引擎算力提升至受制于 CPU 指令吞吐而非内存寻址的物理极限。

## 二、 核心重构阶段记录

整个零分配 (Zero-Allocation) 重构战役划分为四个递进阶段，遵循严格的“基线测量 → 隔离验证 → 算力核收”双轨闭环法则。

### Phase 1: 评估函数的纯 C 化与位域压缩
- **问题**：旧版 `evaluate_board` 占用 47% 的 CPU 时间，主要归咎于生成嵌套数据字典与执行连通域 BFS 计算时的堆分配。
- **实施**：废弃嵌套 `tuple`，采用一维 C 数组（`int[25]`）呈现棋盘。将位置分转化为纯位操作 (Bitmask)。
- **效果**：NPS 从 14.1万 提升至 **37.9万** (约 2.67 倍的增长)。

### Phase 2: 走法生成机制的静态化
- **问题**：`get_valid_moves` 包装生成包含元组的列表对象，产生海量碎片内存。
- **实施**：剥离 Python `list`，改为传入预先分配空间的 16-bit 掩码栈数组指针 (`c_get_ordered_moves`)，并在内部用无符号整数 (`uint16_t`) 映射走法起点、终点和捕获信息。
- **效果**：走法生成耗时剧减 80%，整体 NPS 上探至 **47.0万**。

### Phase 3: 原位回溯与探索容器消解
- **实施**：
  1. **构建安全防护网**：开发微观断言测试 (FEN 测试体系)，保护底层逻辑重构时的分值一致性。
  2. **消除评价与搜索的集合容器**：去除由火炮禁区探测产生的动态 `set` 及双端队列 `deque`。
  3. **数据结构静态化替代**：引入 `c_move_piece` / `c_unmake_piece` 原位操作机制，替换昂贵的状态复制。使用 C 级别静态数组替代原生 Python `dict` 作为置换表 (Transposition Table)。
- **效果**：探针环境下的通讯损耗骤降（带探针速度增长 38%），系统原生裸跑达到 **52.4万 NPS**。

### Phase 4: 解除 Alpha-Beta 堆栈对象分配
- **问题**：实测卡滞于 52.4万。分析测算得出在 `_alpha_beta` 每层深度递归时，引擎均需构造多层 `cdef tuple` 封包返回值，并内部维护 `list` 形式的最佳记录表，这在千万级搜索量下引发客观的内存通信开销。
- **实施**：
  1. **替换返回类型**：将 `_alpha_beta` 的返回由多元组修改为单一浮点数。停止在搜索层内维护最佳路线表。
  2. **分离重路线拼接**：在检索收尾阶段的最外层，提取 `Zobrist TT` 历史缓存构建并复原最佳走子路线。
- **效果**：斩去所有热区的 Python 生成器。单线程无探针测算极速达到 **597,996 NPS**。

## 三、 测试论证与终结结论

### 指标对比
由改造初期的 **110,000 NPS** 到终局基准排压下测试录得数据的 **597,996 NPS**，系统底层框架在摒弃 GC 开销及执行原生数据传唤后，达成了约 5.4 倍的节点测算提升。

### 管线建议
纯 C 语言机制层面的耗时占比已被消弭。为谋求实战棋力的飞跃，后续系统优化的重心应直接移交至：
1. **策略性启发修剪**：重新恢复静默搜索（Quiescence Search）弥补由于剪枝产生的视野盲区。
2. **底层编译重组（可选性能扩展）**：考虑将多个独立运作的 Cython 模块代码整合为一，搭配预调计算指令表及内联（Inline）调用结构，减轻跨文件函数压栈开销。
