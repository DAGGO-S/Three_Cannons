# 残局库技术规范与集成策略

## 1. 核心架构

### 1.1 数据规范
- **局面表述**：统一采用 FEN (Forsyth-Edwards Notation) 字符串作为局面索引。
- **存储格式**：采用 JSONL 格式导出，单条记录包含 `{"fen": str, "eval": float, "game_outcome": float}`。
- **对称性压缩**：利用 D4 对称群（旋转与翻转）进行规范化哈希处理。所有对称局面归约至最小哈希值，存储空间压缩率约 87.5%。

### 1.2 算法原理
- **溯源分析**：通过逆向推演（Retrograde Analysis）迭代计算状态空间。
- **度量指标**：采用 DTM (Distance to Mate) 作为最优路径衡量标准，记录达到绝杀目标的最少步数。
- **搜索无关性 (Search Independence)**：残局库的生成与逻辑判定严禁依赖于任何博弈搜索算法（如 Alpha-Beta 或 MCTS）。它是基于状态平面的拓扑定解，作为搜索引擎的上位“上帝视角”存在。

## 2. 覆盖范围

### 2.1 子力规模
- **三炮体系**：完全覆盖 3 炮对 1-4 兵全量局面。
- **数据规模**：状态空间覆盖量级约 421 万必杀/必败节点。

### 2.2 性能指标
- **检索复杂度**：基于哈希表的 O(1) 检索。
- **内存预热**：程序启动时预加载 `.pkl` 文件至全局缓存 `tablebase_cache`。

## 3. 决策逻辑

### 3.1 胜负判定短路
- **触发条件**：当前局面或首层延伸局面在残局库中存在非零值（Win/Loss）。
- **执行动作**：忽略常规评估分值，强制选取 DTM 最小（进攻）或 DTM 最大（防守）的动作分支。

### 3.2 和棋态处理
- **定位**：残局库判定为和棋（Value=0）时，仅返回基准分数。
- **移交逻辑**：和棋局面下的博弈压力由静态评估函数执行。残局库不执行长程和棋推演，以确保引擎搜索深度。

## 4. 引擎集成规范

### 4.1 哈希校验
必须调用 `get_canonical_hash()` 获取规范化哈希，以匹配库内对称存档。

### 4.2 拦截层级
- **根节点拦截**：在 `find_best_move_iterative_deepening` 入口执行 1-ply 探测，实现瞬时决策。
- **搜索树拦截**：在 Alpha-Beta 搜索的叶子节点或浅层节点执行探测，辅助剪枝。

## 5. 维护规范
- **数据注入**：新生成的子库必须经过 `verify_3c4s_logic.py` 或同类脚本验证。
- **一致性审计**：确保 `GameState` 中的 `cannon_count` 指标与 FEN 解析逻辑严格一致。
