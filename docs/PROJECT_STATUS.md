### 棋力突破路线与瓶颈分析 ⚠️

为了进一步提升 AI 的棋力，必须从以下几个维度的方案进行拆解和攻克：

#### 1. 算法架构选择设定

- **现状与评估**：目前使用 Alpha-Beta 剪枝 + PVS + LMR + 迭代加深的架构。
- **MCTS 考量**：此前已经论证过，对于“三炮十五兵”这种战术复杂度高、步法陷阱密集的非均匀分支游戏，依赖随机采样的 MCTS（蒙特卡洛树搜索）效率通常不如带有强剪枝与优质局部静态评估的 Alpha-Beta 树。因此核心算法路线是合理的，持续深究 AB 树是正确的方向。

#### 2. 每秒访问节点速度提升与瓶颈剖析

- **当下指标评估**：在消除深层堆栈内诸如多元组与列表的封装后（实行去对象结构分配），基准单线程下速度上限至 59.8 万。
- **堵点现状**：目前的 CPU 时间占比仅存于 `c_evaluate_board` 指令、`c_move_piece` 记录以及隔离框架内的函数传唤消耗。
- **预设突破口设计 (基于内联或增量计算)**：如果后续仍需追求数值层面的百万级极速要求，对应的底层改造只剩下合并所有 `.pyx` 文件，附加内联方法调用，并用数据预载取代纯算数机制。
- **中期判定结论**：底层框架已去除了非预期时间开销，其速度基石达标可支撑恢复如静默搜索类等高级启发式修剪战术。

#### 3. 评估函数的盲区与性能瓶颈

- **现状与评估**：纯 C 化与位域转换让静态评估的基准测速获得显著提升。但手工拟合权重参数已接近其固有架构限度。
- **面临的挑战**：为了测量无额外消耗的基准速度临时停用了 QS（静默搜索），导致 AI 的静态评估视野存在显著盲区（难于甄别连环吃子战术漏洞）。
- **突破方案**：下一步不仅需要恢复 QS，还需要在基于位运算的极速 C 评估函数中融入更多的静态局部战术标定，以弥补不搜索时的盲区。

#### 4. 空步裁剪的永久禁用 ⛔

- **现状与评估**：考虑到该游戏存在大量的 Zugzwang (逼走劣局) 情况，而目前没有完善的理论支撑如何解构这些边界条件。
- **[当前结论: 永久禁用]**：在完全解决清楚 Zugzwang 问题之前，重新开启 Null Move Pruning 的动作都是错误的。空步裁剪已被列入黑名单。

#### 5. 定解的残局表与开局库 

- **现状与考量**：到了算力与手工评估函数的极限后，唯有依赖确切的数据表。
- **突破方案**：构建 残局表能够让 AI 在游戏后期获得终局确切解 (Perfect Information)。同时也可引入开局表防止前期走出低级错误。

### 3. 🥉 极致算力内联/魔法表突破 (1M NPS 冲刺)

**理由**: 虽然 59.8万 NPS 已经达到当前无分配基准下的测算顶层，但若进一步追求更高的节点吞吐量，需实施深度的模块合并重构。

| 项目     | 内容                                                                    |
| -------- | ----------------------------------------------------------------------- |
| 问题     | 目前 `c_move_piece`, `c_evaluate_board` 依然在模块级被分别调用。        |
| 技术方案 | 全量重组 `.pxd` 与 `.pyx`，执行 `inline` C 化并提供预运算加成魔法打表。 |
| 预期收益 | 减少模块间的函数压栈，尝试提升至百万级节点阈值。                        |
| 工作量   | 中偏高 (可能造成代码维护性与解耦性的下降)                               |
| 文档参考 | `docs/ref/REF_Zero_Allocation_Optimization.md` 客观实录的剖析           |
