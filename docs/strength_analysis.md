# Three Cannons 棋力提升路径分析

> 本文档用于持续记录关于棋力提升的思考和决策，避免重复讨论。

## 当前状态（2026-03-07）

| 指标              | 值                                         |
| ----------------- | ------------------------------------------ |
| 搜索算法          | Alpha-Beta + PVS + LMR + 迭代加深          |
| 评估函数          | V10：BFS 控制区 + 材料分 + 位置分 + 贴炮分 |
| 静默搜索          | 有，深度限制 8                             |
| 置换表            | 定长 2^21 数组                             |
| Null Move Pruning | 已禁用（Zugzwang 问题）                    |
| 深度 12 耗时      | 3.26 秒                                    |
| 深度 16 耗时      | >1 分钟（推算，倍率 ~1.75）                |
| 作者自我评估      | 棋力 ≈ 深度 16                             |

## 核心困境

**"搜索深度-棋力"天花板**：手写评估函数已难以再提升，棋力只能靠加深搜索来提升。但 depth 每多 1 层耗时增加 ~1.75x，从 depth 12（3.26s）到 depth 16（~17s 推算）到 depth 20（~90s 推算），速度增长不可持续。

这不是评估函数"不够好"的问题，而是**搜索深度与评估精度的替代关系**问题：
- 浅搜索 + 精细评估 → 能"猜"对大部分局面，但对战术组合视而不见
- 深搜索 + 粗糙评估 → 能"看见"战术，但需要极快的底层

当前引擎卡在中间：评估已经足够精细，但底层不够快，导致深度不够深。

## 路径分析（按可行性排序）

### 路径 A：底层加速 → 多搜 3-4 层

**核心思路**：不改算法，只让每个节点更快。

| 技术                                | 预估加速 | 额外深度 | 工作量 | 风险                           |
| ----------------------------------- | -------- | -------- | ------ | ------------------------------ |
| Make/Unmake + C 数组 board          | 3-5x     | +2-3 层  | 高     | 中（需重构 history、GUI 接口） |
| 走法整数化 + C 栈                   | 1.5-2x   | +1 层    | 中     | 低                             |
| evaluate_board 中 BFS 改为 C 级实现 | 2x       | +1 层    | 中     | 低                             |

合计可能达到 **depth 15-16 在 3 秒内**。

**评价**：实际意义是"把你 1 分钟才能走到的棋力压缩到 3 秒"。有意义，但不改变棋力上限。

---

### 路径 B：残局表 (Endgame Tablebase) ← **强烈推荐**

**核心思路**：棋盘只有 5×5 = 25 格，棋子总数有限。当兵数 ≤ 6-7 时，所有局面可以**穷举并预计算**。

**可行性分析**：
- 3 炮固定存在 + N 兵，每个棋子占 1 格
- 3 炮在 25 格中的排列：C(25,3) = 2,300
- 6 兵在剩余 22 格中的排列：C(22,6) = 74,613
- 考虑双方回合：总局面数 = 2,300 × 74,613 × 2 ≈ **3.43 亿**
- 每个局面存 1 byte（胜/负/和 + 距离）≈ **~340 MB**

5 兵以下更小：
- 5 兵：2,300 × C(22,5) × 2 ≈ **1.2 亿**（~120 MB）
- 4 兵：2,300 × C(22,4) × 2 ≈ **3,400 万**（~34 MB）

**意义**：当残局表覆盖到 ≤6 兵时，一吃到剩 6 个兵，引擎瞬间知道**绝对正确的结果**。这等价于在那个时刻拥有无限搜索深度。评估函数在残局阶段彻底被完美信息取代。

**实现方案**：逆向搜索（Retrograde Analysis）。从所有终局状态（0 兵 = 炮胜，所有炮被困 = 兵胜）出发，反向标记所有父状态的胜负。

---

### 路径 C：重新启用 Null Move Pruning

**NMP 被禁用的原因**：Zugzwang（被迫走棋反而不利）。在三炮棋中，炮方确实可能出现 Zugzwang。

**解决方案**：不是完全禁用，而是**有条件启用**：
- 只在炮方（maximizing）使用 NMP，兵方不用（兵方 Zugzwang 少见）
- 或在非 PV 节点且评估值远高于 beta 时才使用
- R=2 而非 R=3 以降低风险

**预估收益**：在不增加耗时的情况下等效+1~2层。

---

### 路径 D：NNUE / 神经网络评估函数

**核心思路**：用自对弈生成训练数据，训练一个小型神经网络替代手写评估。

**评价**：技术上完全可行（5×5 棋盘输入极小），但工作量巨大（训练框架、数据生成、嵌入 Cython）。**建议等路径 A/B 都耗尽后再考虑。**

---

### 路径 E：AlphaZero / MCTS

**评价**：之前的对话（aa4f3196）已经探索过 Nash 训练，遇到了训练稳定性问题。经典 AB 搜索在小棋盘上通常优于 MCTS，因为精确剪枝比统计采样更高效。**不推荐。**

---

## 推荐行动优先级

1. 🏆 **路径 B（残局表）**：一次性投入，永久收益。从 ≤4 兵开始（~34 MB），逐步扩展。这是唯一能**定性改变棋力**的方案——从"猜"变成"知道"。
2. 🥈 **路径 C（重启 NMP）**：小工作量，等效+1-2层。
3. 🥉 **路径 A（底层加速）**：中等工作量，量变而非质变。
