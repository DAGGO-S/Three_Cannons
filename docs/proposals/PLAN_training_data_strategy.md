# 训练数据策略：eval 分数与 game_outcome 胜负的权重取舍

> **状态**：PLAN（探讨期，待提炼为 TASK 或删除）
> **提出时间**：2026-03-10

---

## 一、问题背景

当前自对弈生成器 (`scripts/self_play_generator.py`) 产出的每条 JSONL 记录包含两个监督信号：

| 字段           | 类型                          | 来源                        |
| -------------- | ----------------------------- | --------------------------- |
| `eval`         | 浮点数，范围约 -10000 ~ 10000 | `evaluate_board()` 静态评估 |
| `game_outcome` | 0.0 / 0.5 / 1.0               | 该局最终胜方（回溯性标签）  |

两个信号的意义不同，但都可以作为学习目标。如何取舍是核心设计问题。

---

## 二、信号质量分析

### 2.1 game_outcome（胜负标签）

**优点**：

- 客观。不依赖人工调参的评估权重，直接反映棋局结果。
- 适合二分类或回归训练（价值网络）。
- 即使对局双方水平较低，胜负本身是准确的。

**缺点**：

- 信息稀疏。整局 N 步走法共享同一个标签（-10000 步局面全值相同）。
- 对中间过程没有区分度：一个"已经赢定"的局面和"勉强均势"的局面，标签相同。

### 2.2 eval（静态评估分）

**优点**：

- 信息密度高，每一步的局面都有独立的分值。
- 能区分"形势稍差"和"形势极差"。
- 可直接作为回归目标训练值估计网络。

**缺点**：

- 依赖手搓权重。当前 `evaluate_board()` 的权重是人工设定，存在系统性偏差。
- 无法反映战术深度（0层评估看不出强制杀）。
- 若手搓权重本身有误，则 eval 分训练出的网络会继承这些误差。

---

## 三、低水平对打数据的局限性

当前炮方深度 5、兵方深度 3，属于中低水平对局。存在以下风险：

**风险一：系统性走法偏差**

低水平 AI 会反复掉入同类型陷阱，产出局面重复度高，覆盖率低的数据集。极端残局（如"炮被完全包围"）出现概率偏低。

**风险二：伪最优路径**

低水平 AI 找到的"胜法"不一定是最短路径，导致 game_outcome=炮赢 的局面中有大量次优走法，会混淆价值网络的学习目标。

**风险三：eval 信号与结果不对齐**

对于炮方，静态分 -1360 的局面在低水平对局中可能最终炮赢，在高水平对局中炮输。这导致 eval 和 game_outcome 给出矛盾的训练信号。

---

## 四、改进方向

按优先级排列：

### 方向 A：提升数据覆盖率（短期，可立即执行）

增加 epsilon 随机概率（如从 0.15 调至 0.25），或引入随机开局 FEN，确保数据集覆盖多样局面，减少重复模式。

**验收标准**：统计 JSONL 中唯一 FEN 的占比，目标 > 85%。

### 方向 B：双信号协同训练（中期）

训练时同时使用两个信号，各负责不同层次：

- `eval` 作为辅助特征（输入），不作为唯一学习目标。
- `game_outcome` 作为主标签，指导价值网络的输出方向。

两者不矛盾时互相强化；矛盾时以 `game_outcome` 为准。

**验收标准**：训练完成的网络在残局库测试集（如 Endgame01.json）上的预测准确率，对比纯 eval 或纯 game_outcome 训练的基线。

### 方向 C：迭代自提升（长期，AlphaZero 路线）

初期数据训练出第一代网络 V1，用 V1 替换静态评估重新生成数据，然后训练 V2，如此迭代。每轮数据质量因网络性能提升而改善，最终脱离手搓权重依赖。

**前提条件**：V1 网络必须在硬件上推理速度足够快，不能让搜索速度下降超过 50%。

---

## 五、当前阶段建议

当前阶段（数据积累期）优先执行方向 A。方向 B 与 C 等数据量达到约 5 万条局面后再评估是否启动 TASK。

> 本文档在讨论出可执行方案后，提炼为对应 TASK 并删除。



**核心矛盾**

当前静态评估 `evaluate_board()` 在 C 层运行，每次调用 < 1μs。
PyTorch 网络哪怕是最小的 MLP，单次推理也需要 0.1-1ms（Python 调度开销）。

在深度 6 的 Alpha-Beta 搜索中，叶节点评估调用次数可达 10^5 量级。

* 手搓静态：10^5 × 1μs = **0.1 秒**
* 小型网络：10^5 × 0.5ms =  **50 秒** （慢 500 倍）

---

**三条可行路线**

| 方案                | 原理                                                         | 代价                                  |
| ------------------- | ------------------------------------------------------------ | ------------------------------------- |
| **极小网络 + ONNX** | 2层 MLP，输入 25 个格子的 one-hot，ONNX Runtime 推理         | 单次推理可压到 < 0.05ms，损失部分精度 |
| **批量评估**        | 搜索不在叶节点立即评估，收集一批叶节点再整批送网络           | 需要重构搜索为 BFS/分层，工程量大     |
| **浅搜索 + 网络**   | 搜索深度降到 2-3，用更强的网络弥补深度不足（AlphaZero 路线） | 彻底重构搜索逻辑                      |

---

**当前阶段建议**

**极小网络 + ONNX** 是性价比最高的路线：

* 输入：25个格子的棋子编码（3分类 → 25×3=75维 或直接 25 维整数）
* 网络：Linear(25→64) → ReLU → Linear(64→32) → ReLU → Linear(32→1)（约 3000 个参数）
* 导出：PyTorch → ONNX，用 `onnxruntime` 推理，Python GIL 开销最小
* 目标：单次推理 < 0.05ms，搜索速度降幅 < 10 倍

这个方向在数据积累到 5 万局后值得立一个 `PLAN_` 提案。
