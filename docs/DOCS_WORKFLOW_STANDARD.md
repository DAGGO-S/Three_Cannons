# 文档状态机与生命周期工作流标准 (Docs Workflow Standard)

> **制定时间**：2026-03-10
> **适用对象**：所有参与本项目的开发者与 AI 智能体 (Agents)

为了确保在高频迭代的算法博弈项目中，知识库具备**高纯净度**、**无幻觉**及**极高信噪比**，本项目 `docs/` 目录下的所有文件必须严格遵循“前缀 + 子目录”的状态机流转法则。文档不再是静态读物，而是伴随代码同生共死的生命周期管理池。

---

## 📂 空间目录划分与状态流转机制

`docs/` 目录被严格划分为以下五个功能子域。各子域内的文件必须携带对应的状态前缀。

### 1. `proposals/` (提案与探讨期)
* **包含前缀**：`PLAN_`, `WIP_`, `SUGGEST_`
* **职能形态**：存储头脑风暴、探索性方案比较（Pros/Cons分析）、架构改动初稿、以及暂时因风险/时间原因挂起的技术债提议。
* **生命周期约束**：**极短或挂起**。对于 `PLAN_` 与 `WIP_`，当讨论得出一个可以落地执行的最终结论后，必须立刻被转移（转化为 TASK）或被**硬性删除**。绝不允许半成品逻辑长期驻留，导致后续 AI 读取时产生思路幻觉。
* **准入示例**：`SUGGEST_performance_optimization.md`

### 2. `tasks/` (执行与验证期)
* **包含前缀**：`TASK_`
* **职能形态**：从 Proposals 中提炼出的、带有量化验收标准（断言红线或 NPS 数据指标）的勾选单（Checkbox 表单）。
* **生命周期约束**：伴随开发周期存在。当任务的代码改动满足了其对应的测试网络及 AB 性能测试后（即达成“闭环”），该文件被标记为 `[x]` 完成态。此时，该任务文件在提炼核心价值后，必须被移出本目录（归档或销毁）。
* **准入示例**：`TASK_data_refactor.md`

### 3. `ref/` (收口与固化资产库)
* **包含前缀**：`REF_`
* **职能形态**：代表系统当前视角的**技术溯源基准** (Single Source of Truth)。包含定型的系统架构、确凿的纯净测算复盘、已固化的接口契约。
* **生命周期约束**：**永久存续**（直至被推翻迭代）。
* **写作铁律**：此目录下的文字必须**坚持冷峻、客观、数据驱动**。禁止任何情绪化、邀功式字眼，禁止中英夹杂。这是其他 AI 接手项目时的第一输入源。
* **准入示例**：`REF_architecture.md`, `REF_Zero_Allocation_Optimization.md`

### 4. `guides/` (操作指南与外围引导)
* **包含前缀**：`GUIDE_`
* **职能形态**：面向外部人类用户或新介入开发者的操作手册，如跑测指令、界面操作法、编译引导。
* **准入示例**：`GUIDE_getting_started.md`

### 5. `logs/` (系统状态与动态流水)
* **包含前缀**：无强制前缀，或约定俗成的流水账。
* **职能形态**：记载项目每日/每轮会话的进度滚动报表，以及压测日志的历史存档。
* **准入示例**：`progress.md`, `PROJECT_STATUS.md` (总看板置于根目录或此目录), `performance_log.md`

---

## 🔄 双重闭环工作流 (The Closed-Loop Workflow)

在一项重构或新特性被固化为 `REF_` 资产前，文档必须亲历以下闭环映射：

1. **萌芽 (Proposals)**：生成 `PLAN_`。撰写隔离测试法与影响面。
2. **定调 (Tasks)**：确认方案。删除或封存 `PLAN_`，新建 `TASK_`。定下可验证的底层测试基调（如 `bench_fixed_depth.py` 的初始跑分或 FEN 断言）。
3. **干活 (Execute/Test)**：在代码层实施，且代码**必须**100%跑通所有测试，并拿到真实的对照组性能数据。这就是“通过第一性原理验证代码真伪及其效能”。
4. **飞升 (Reference)**：将 `TASK_` 打钩完结。并将其中的成功机制提炼、纯净数据提取，浓缩为一份纯客观的 `REF_` 放入 `ref/` 目录。随后，归档或清理旧的 `TASK_` 档案。

> 严格遵守上述从“发散 -> 拟定 -> 清算”的管道化管理，是保证本项目 AI Agent 读取效率与架构清晰度的唯一法则。
