# 文档状态机与生命周期工作流标准 (Docs Workflow Standard)

> **制定时间**：2026-03-22 (更新版)
> **适用对象**：所有参与本项目的开发者与 AI 智能体 (Agents)

为了确保知识库具备**高纯净度**、**无幻觉**及**极高信噪比**，本项目 `docs/` 目录下的所有文件必须严格遵循“职能模块化 + 状态机流转”法则。

---

## 📂 空间目录划分与状态流转机制

### 1. `proposals/` (提案与探讨期)
* **包含前缀**：`PLAN_`, `WIP_`, `SUGGEST_`
* **生命周期**：**极短或挂起**。结论达成后转化为 TASK 或被硬性删除。

### 2. `tasks/` (执行与验证期)
* **包含前缀**：`TASK_`
* **职能形态**：带有量化验收标准的勾选单。
* **生命周期**：代码闭环后，提炼价值至 REF，随后删除或归档原始 Task。

### 3. `specs/` (技术规格书) - [核心资产]
* **包含前缀**：`SPEC_`
* **职能形态**：存储静态、稳定的数据协议、通信格式与标准。
* **准入示例**：`SPEC_FEN_FORMAT.md`, `SPEC_DATA_PROTOCOL.md`

### 4. `ref/` (技术参考资产库) - [核心资产]
必须按二级分类前缀存储：
* `REF_ARCH_`: 宏观架构、拓扑、分层职责与设计决策。
* `REF_ALGO_`: 算法公式、搜索理论、评估模型及演进历史。
* `REF_INTERFACE_`: API 签名、参数契约、调用序列图。
* `REF_DEBT_`: 已知系统性技术债与未来演进路线。

### 5. `experiments/` (实验场) - [观测站]
* **包含前缀**：`EXP_`
* **职能形态**：存储具备科学规律的定量对比数据（如 A/B Test、模型 Elo 跑分）。
* **准入示例**：`EXP_20260318_weight_battle.md`

### 6. `guides/` (操作指南)
* **包含前缀**：`GUIDE_`
* **准入示例**：`GUIDE_getting_started.md`

---

## 🔄 “减熵提炼”工作流 (Value Extraction)

在 `TASK_` 标记完成后，必须执行以下提炼至 `REF_` 的标准操作：

1. **Fact (硬指标)**：记录本次任务最终达成的物理指标（如 18.2M NPS）。
2. **Logic (改动链)**：提炼物理实现逻辑，包括关键函数更名或数据流向改变。
3. **Constraint (新约束)**：确立由此产生的新代码红线（规则逻辑边界）。

---

## ⚖️ 写作铁律
- **坚持冷峻、客观、数据驱动**。
- **正向事实陈述**：禁止使用“为什么”、“不要”、“判断”等引导。
- **知识压缩**：拒绝冗余，每份文档必须是 Single Source of Truth。
