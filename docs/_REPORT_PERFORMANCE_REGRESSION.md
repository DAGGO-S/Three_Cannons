# 性能闭环反思报告：第一性原理下的算力瓶颈重新定位

## 1. 现象与数据背离（客观事实）
在执行了 **TASK_01_阶段四（原位覆写状态机，消除 GameState 对象的实例化）** 后，我们收集了以下基准测试数据（统一使用 `scripts/bench_fixed_depth.py`）：
* **重构前 (Baseline)**: ~ 490,671 NPS
* **重构后 (Zero-Allocation Attempt)**: ~ 477,018 NPS

**结论**：原位修改并未带来预期的“数量级跃升”，反而引发了轻微的性能倒退（-2.7%），并使得上层的 MVC 模型状态隔离逻辑陷入大面积崩溃。这一现象打破了原有的“闭环有效性”预期，当前正处于瞎折腾的开环边缘。

## 2. 批判性分析：为什么手段偏离了目标？
我们的根本目标是：**穿透博弈树搜索的算力瓶颈，使其逼近物理极限。**
之前的分析认为，瓶颈在于**内存对象的不断新建（Malloc）和垃圾回收（GC）**。这在纯净的虚拟机解释层是绝对正确的。
但我们忽略了以下事实：

### A. Cython 编译期的黑盒优化
在 `c_move_piece` 返回新对象时，这部分代码是通过 Cython 编译并在底层用 `memcpy` 复制了一块 25 长度的 C 数组。在现代 CPU 的 L1/L2 缓存中，复制极小的一块内存（100 Bytes）的微指令速度，可能被编译器的高度向量化（SIMD）优化得**比执行分支判断（记录并还原被吃掉的棋子等反操作）还要快**。

### B. unmake_move 的隐性成本
在 Alpha-Beta 热点循环中，为了实现在同一块内存上复用，我们引入了 `c_unmake_piece`。这意味着走入分支需要执行一次状态改写，退出分支又需要执行一次反向状态改写。虽然消除了对象新建，却让底层的纯位操作指令数翻了一倍。

### C. 真正的算力黑洞究竟在哪里？
NPS 只有不到 50 万，对于纯 C 级的位运算而言是非常缓慢的。真正的阻塞点必然还在**某些隐蔽的 Python 边界交互**或**极大计算复杂度的循环**中。我们目前是在凭借猜测调优（手段），而非依据 Profiler 数据调优（事实）。
